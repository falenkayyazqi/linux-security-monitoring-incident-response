# SSH Authentication Monitoring & Brute-Force Detection

**Language:** English | [Versi Bahasa Indonesia](detection-analysis.id.md)

## Objective

Build a lightweight Python-based log monitor to analyze Ubuntu `/var/log/auth.log` and detect SSH brute-force authentication patterns.

The monitoring focuses on:

- Failed SSH authentication
- Successful SSH authentication
- Brute-force attempts based on the number of failures within a sliding time window
- Sudo activity as supporting authentication and security telemetry

## Detection Configuration

- Log source: `/var/log/auth.log`
- Threshold: 5 failed authentication attempts
- Time window: 5 minutes
- Tracking key: source IP + username
- Analysis period:
  - Since: `2026-09-25T17:59:00+07:00`
  - Until: `2026-09-25T18:04:30+07:00`

## Simulation

Authentication activity was generated from the Kali Linux VM:

- Source IP: `192.168.82.130`
- Target Ubuntu server IP: `192.168.82.129`

The simulation generated failed SSH authentication attempts against `admin`, `root`, and `test`.

The `test` account received 6 failed password attempts within the analysis period, allowing the detector to reach the configured threshold. A successful SSH authentication using public-key authentication was also generated for the `user` account.

## Detection Results

The detector processed the defined analysis window and produced:

- Failed logins: 10
- Accepted logins: 1
- Sudo commands: 0
- Alerts raised: 1

The alert was **`BRUTE-FORCE ATTEMPT`** with these details:

- Source IP: `192.168.82.130`
- Target username: `test`
- Detection point: `2026-09-25T18:01:56.577144+07:00`
- Failed attempts within 5 minutes: `5`

## Authentication Analysis

The failed authentication events were associated with password authentication attempts. The successful authentication event had the following attributes:

- Username: `user`
- Source IP: `192.168.82.130`
- Authentication method: `publickey`

The detector therefore did not classify the successful public-key login as a successful password compromise event.

## Evidence

Supporting evidence is stored in `evidence/`:

- `ssh-auth-log.txt` - filtered SSH authentication events from the simulation window
- `monitor-output.txt` - console output generated by the Python detector
- `alerts.json` - structured detection results
- `sudo-activity.txt` - filtered sudo activity for the same analysis window

## Limitations

This is a lightweight host-based monitoring exercise, not a replacement for a production SIEM or IDS/IPS platform. The detector analyzes a local authentication log and applies a threshold-based rule. It does not provide:

- Centralized log collection
- Persistent alerting
- Automated response
- IP reputation analysis
- Correlation across multiple hosts
- Advanced behavioral detection

## Security Considerations

SSH password authentication was temporarily enabled only for the controlled lab simulation. After the simulation, the original SSH configuration was restored and validated with `PasswordAuthentication no`. SSH service status was also verified as active after the configuration was restored.

## Conclusion

The lab demonstrates a basic SOC-style workflow:

1. Generate controlled authentication activity.
2. Collect authentication logs.
3. Parse relevant SSH events.
4. Correlate failures by source IP and username.
5. Apply a threshold-based detection rule.
6. Generate a structured alert.
7. Preserve supporting evidence.
8. Restore the server to its hardened configuration.
